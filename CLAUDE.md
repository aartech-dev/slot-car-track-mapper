# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A device for mapping a slot car track by fusing an optical-mouse sensor (X/Y motion) with an IMU (heading) into a dead-reckoned path. This is MicroPython firmware for a **Raspberry Pi Pico 2 W** (RP2350) — there is no package manager, build step, linter, or test suite. Code is deployed by copying `.py` files directly onto the board (e.g. via Thonny) where they run as `main.py`.

`main.py` runs the actual fusion loop now (PMW3360 + ICM-42688-P + IR lap sensor, on a Pico 2 W) — **not yet tested on real hardware**, and it has one known-fake piece: `pmw3360.py`'s `SROM_FIRMWARE` is a zeroed placeholder, the same situation `a6_binary.py`/`main.py` used to be in for the ADNS-9800, just not yet resolved for the new sensor. `a6_binary.py` and the ADNS-9800 register map it fed are now historical only — superseded, not a reference pattern to follow (the PMW3360 driver in `pmw3360.py` is the current pattern).

The physical build is a cut-and-graft of a donor **Scaleauto HS-124** slot car chassis: the stock rear motor/drive section is kept, and the front section is replaced by a custom sensor fixture on a sled/skid (no front wheels) — see `DESIGN.md` §7 for the full mechanical plan, constraints, and open risks. Reference photos of the donor chassis are in `tmp/`.

## Design

`DESIGN.md` is the working design document for the mapping approach: why a single optical-flow sensor alone can't reconstruct track curvature (it reports body-frame displacement, not world-frame position), the IMU-fusion approach chosen to fix that, and the power-delivery plan for running electronics off analog (non-PWM) rail voltage, which sags toward 0V at low throttle. Read it before making sensing/power/fixture decisions — it's the source of truth for *why*, this file is only the *where things are*. §9 ties the whole pipeline together into the actual end goal — an accurate vector map of *every* lane, not just one — and §10 covers whether a better IMU would reduce drift (yes, but the software mitigations already in place get most of the achievable improvement for free).

`BRINGUP.md` is the staged hardware/firmware validation plan for going from parts-in-hand to a working data-collection run — solo sensor bring-up on a breadboard before combined bring-up, before mechanical fixture fabrication, before the irreversible chassis cut, before rail power + motor are ever added to the mix. Follow it in order when actually building this rather than improvising a bring-up sequence — each stage exists to isolate a specific class of failure from the ones before and after it.

`BOM.md` is the complete parts list (electronics, mechanical, consumables) for one fixture, with a status column (confirmed vs. still-TBD part/value) — the shopping list companion to `DESIGN.md` §8's open items, which explain *why* each TBD is still open.

## Files

- `main.py` — the firmware entry point. Initializes the PMW3360 (SPI0) and ICM-42688-P (I2C0), runs `calibrate_gyro_bias()` (`DESIGN.md` §6 — averages the stationary gyro for `GYRO_CAL_DURATION_MS` and checks accelerometer variance to catch a car that moved during calibration), then runs the fusion loop: integrate bias-corrected gyro yaw into heading, apply the lever-arm correction (`LEVER_ARM_MM = 18.0`, from the CAD), rotate into world coordinates, accumulate (x, y), and log every sample as a CSV row to `track_log.csv` on flash (flushed every `FLUSH_EVERY` samples — deliberate, given §4's power-reliability story makes a mid-run brownout a real risk, not a theoretical one). Stops after `LAPS_TO_RECORD` lap-marker crossings (IR sensor on GPIO26/ADC0) or `MAX_RUN_MS`, whichever comes first, resetting (x, y) to (0, 0) at each crossing. Read the module docstring before trusting a run — it lists the calibration steps still needed on real hardware (real SROM firmware, `LAP_THRESHOLD` against the actual marker, gyro-sign/optical-axis sanity checks, and confirming the gyro-bias stillness threshold against real accelerometer noise).
- `pmw3360.py` — PMW3360 SPI driver (register map, motion-burst read, CPI-to-mm conversion). `SROM_FIRMWARE` is a zeroed placeholder, not the real firmware blob — see the module docstring for why, and what to replace it with.
- `icm42688.py` — ICM-42688-P I2C driver (WHO_AM_I check, low-noise mode config, raw/converted gyro+accel reads). Only gyro Z feeds the fusion loop today; accel is read but unused, kept for future crash-detection/roll-pitch work.
- `a6_binary.py` — **historical, not used by current firmware.** A desktop-only conversion script (adapted from `mrjohnk/ADNS-9800`) that embeds the *ADNS-9800's* SROM as a `frame` byte array and writes it to `adns_9800_srom_a6.bin` when run with `python a6_binary.py` on a regular computer. Left in place as a worked example of "how to turn a vendor SROM binary into a Python byte array" — that's the technique still needed for `pmw3360.py`'s placeholder, just with the PMW3360's own SROM file instead of the ADNS-9800's.
- `wifimanager.py` — an async `WiFiManager` class (`network` + `asyncio`, MicroPython-only) that connects to a list of known SSIDs and monitors/reconnects. Hardcoded `WIFI_NETWORKS` credentials near the bottom are placeholders. Standalone: not currently imported by `main.py`.
- `README.md` — the *original* design notes/scratchpad, from before this project settled on PMW3360/ICM-42688-P/Pico 2 W — largely superseded by `DESIGN.md` now. Its SROM/SD-card conversion walkthrough is ADNS-9800-specific and no longer the plan.
- `cad/fixture.scad` — parametric OpenSCAD model of the front sensor fixture (`DESIGN.md` §7). All donor-chassis dimensions are now from calipers, including the front-of-motor carrier's wedge-and-tab profile (`tmp/chassis-front-of-motor.jpeg`) that the kept rear section presents at the cut instead of a flat face — `carrier_interface()` notches the fixture's leading edge to mirror that exact outline (a flush, self-aligning butt joint, `carrier_h` = 3.5mm thick to match), which elongated the fixture to a measured 102.5mm total (up from the original ~65mm estimate). The second (rear) guide pin no longer has fixture-side geometry (no more `rear_guide_mount()`); it now uses a small pre-existing hole near the carrier's tab tip instead of a molded boss. The deck itself IS the PMW3360 datasheet's (`tmp/C20612443.pdf`) "Customer Supplied Base Plate with Recommended Opening" (Fig. 8) — `pmw_lens_pocket()` cuts that exact stepped opening into it (an outer counterbore leaving the datasheet's recommended 2.4mm base-plate thickness, plus a smaller through-hole for the optical path), sized from the real PMW3360DM-T2QU + LM19-LSI mechanical drawing rather than a generic placeholder. `shared_pcb()` models the datasheet's "Customer Supplied PCB" counterpart (Fig. 5): one 1.11mm strip board, mounted on standoffs above the deck, carrying the Pico 2 W (rotated 90° to fit — still tight), the PMW3360 chip, the ICM-42688-P, and the IR lap sensor together, wired point-to-point along the board's copper strips rather than as four separate breakouts; only the PMW3360's lens and the IR sensor's bent leads reach back down through the deck (`pmw_lens_pocket()` / `ir_lead_hole()`). The IR sensor is sized as QRE1113 (measured from `tmp/QRE1113.pdf`) rather than TCRT5000 (`tmp/TCRT5000.pdf`), since TCRT5000's 7mm body doesn't fit the fixture's available ground clearance. Still not print-ready: the ICM-42688-P footprint is a typical/placeholder value, and the PMW3360 lens pocket simplifies Fig. 8's real tapered "D"-shaped opening into straight rounded rectangles. Render with `openscad --autocenter --viewall -o preview.png cad/fixture.scad`; its `echo()` output reports the computed fixture length, the lever-arm `r` for the fusion loop's correction (`DESIGN.md` §2), the carrier interface and PMW3360 pocket dimensions, the shared PCB's computed footprint, and flags any standoff or board-width margin that comes out negative/oversized.
- `electronics/electronics.kicad_sch` — single-sheet KiCad schematic covering every electrical component (`DESIGN.md` §3 addendum): rail power input, reverse-polarity protection, buck-boost regulator, supercap (with an R1+D2 charge-inrush limiter — DESIGN.md §4), Pico 2 W, PMW3360, ICM-42688-P, IR reflectance sensor. Passes ERC clean. The GPIO pin assignments it settled (SPI0 on GPIO10-13, PMW3360 MOTION on GPIO14, I2C0 on GPIO4/5, ICM interrupt on GPIO6, IR sensor on GPIO26/ADC0) are exactly what `main.py` uses. Regulator/sensor modules are drawn as generic labeled connectors, not real part symbols — see the schematic's own text notes. `electronics/preview.png` is a rendered reference; regenerate with `kicad-cli sch export svg`.
- `sim/simulate_track_run.py` — desktop-only (plain Python, no MicroPython/hardware deps) generator of the sensor data `main.py` should see driving a real track: parses a lane out of an SVG track plan (`tmp/bolton-track.svg`), builds a curvature-limited speed profile, and synthesizes PMW3360/ICM-42688-P/IR readings including realistic noise/bias — output at `sim/expected_track_run.csv`, over `N_LAPS` (5) continuous simulated laps. Also re-runs `main.py`'s own fusion math over its synthetic output as a validation check (the `recon_*` columns) and emits `sim/expected_firmware_log.csv`, formatted exactly like the real on-device `track_log.csv` (used to test `tools/closed_loop_correct.py` without hardware). Re-run after changing any constant it mirrors from `main.py` (CPI, `LEVER_ARM_MM`, `LAP_THRESHOLD`, `LAPS_TO_RECORD`) to keep it in sync.
- `tools/plot_track_csv.py` — renders either CSV shape this project produces (the firmware's `track_log.csv`, or the simulator's `expected_track_run.csv`) as a browsable SVG map. Auto-detects which by column names. For the simulator shape, overlays ground truth against the reconstructed path — note it rotates the reconstruction by the true initial heading before overlaying, because `main.py`'s (x,y) frame has its x-axis aligned to the car's *initial* heading, not the world's absolute X axis; skipping that rotation is what made an early version of this comparison look far worse than the reconstruction actually is.
- `tools/closed_loop_correct.py` — offline (desktop, run on a downloaded `track_log.csv`) closed-loop gyro correction, `DESIGN.md` §6; the full procedure is `BRINGUP.md` Stage 11. Needs no firmware change: recovers per-tick heading and body-frame motion directly from the logged `theta_rad`/`x_mm`/`y_mm` columns (theta accumulates continuously in `main.py`, never resetting), then re-integrates each completed lap with a constant bias correction that makes its net heading change match `--net-turns` (a required argument — the track's known net rotation per lap, determined by inspecting the driven lane, not guessed). Cut the simulated closing error by ~40% in testing. Prints each lap's length in meters and the cross-lap mean/spread — this is the tool that answers "how long is the lap." `--average-out` resamples and averages multiple corrected laps into one smoothed shape CSV; treat its own length figure as secondary to the per-lap mean (it doesn't correct for small cross-lap orientation differences before averaging, which measurably inflated its length in testing).

## Architecture notes

- **PMW3360 protocol** (`pmw3360.py`): SPI register device, write with the MSB of the address set (`reg | 0x80`), read with it clear (`reg & 0x7F`). Bring-up is reset → discard stale motion registers → upload SROM firmware via burst mode → verify product ID (0x42) and SROM ID → set resolution (CPI). Steady-state reads use `Motion_Burst` (0x50), a single 12-byte burst covering motion status + delta X/Y + quality, rather than separate register reads.
- **ICM-42688-P protocol** (`icm42688.py`): I2C, `WHO_AM_I` (0x75) should read 0x47. `PWR_MGMT0` enables gyro+accel low-noise mode; needs ~50ms settling before readings are valid. Accel+gyro XYZ read as one 12-byte burst starting at `ACCEL_DATA_X1` (0x1F) — the two blocks are contiguous.
- **Gyro-bias calibration** (`main.py`, `DESIGN.md` §6): once at startup, before the fusion loop — averages the stationary gyro Z reading over `GYRO_CAL_DURATION_MS` into `gz_bias`, subtracted from every gyro reading for the rest of that run. Also checks accelerometer variance over the same window and warns if the car wasn't actually still. Re-measured every run, not cached — gyro bias drifts with temperature/time. Corrects only the static bias present at power-up, not in-run wander.
- **Fusion loop** (`main.py`, `DESIGN.md` §6): per tick, integrate bias-corrected gyro Z into heading, pull (dx, dy) off the PMW3360, apply the lever-arm correction, rotate into world frame, accumulate (x, y), log a CSV row, flush periodically. Lap crossings (IR sensor, debounced) reset (x, y) to (0, 0) and stop the run after `LAPS_TO_RECORD`.
