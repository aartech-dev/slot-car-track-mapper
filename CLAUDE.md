# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A device for mapping a slot car track by fusing an optical-mouse sensor (X/Y motion) with an IMU (heading) into a dead-reckoned path. This is MicroPython firmware for a **Raspberry Pi Pico 2 W** (RP2350) — there is no package manager, build step, linter, or test suite. Code is deployed by copying `.py` files directly onto the board (e.g. via Thonny) where they run as `main.py`.

`main.py` runs the actual fusion loop now (PMW3360 + ICM-42688-P + IR lap sensor, on a Pico 2 W) — **not yet tested on real hardware**, and it has one known-fake piece: `pmw3360.py`'s `SROM_FIRMWARE` is a zeroed placeholder, the same situation `a6_binary.py`/`main.py` used to be in for the ADNS-9800, just not yet resolved for the new sensor. `a6_binary.py` and the ADNS-9800 register map it fed are now historical only — superseded, not a reference pattern to follow (the PMW3360 driver in `pmw3360.py` is the current pattern).

The physical build is a cut-and-graft of a donor **Scaleauto HS-124** slot car chassis: the stock rear motor/drive section is kept, and the front section is replaced by a custom sensor fixture on a sled/skid (no front wheels) — see `DESIGN.md` §7 for the full mechanical plan, constraints, and open risks. Reference photos of the donor chassis are in `tmp/`.

## Design

`DESIGN.md` is the working design document for the mapping approach: why a single optical-flow sensor alone can't reconstruct track curvature (it reports body-frame displacement, not world-frame position), the IMU-fusion approach chosen to fix that, and the power-delivery plan for running electronics off analog (non-PWM) rail voltage, which sags toward 0V at low throttle. Read it before making sensing/power/fixture decisions — it's the source of truth for *why*, this file is only the *where things are*.

`BRINGUP.md` is the staged hardware/firmware validation plan for going from parts-in-hand to a working data-collection run — solo sensor bring-up on a breadboard before combined bring-up, before mechanical fixture fabrication, before the irreversible chassis cut, before rail power + motor are ever added to the mix. Follow it in order when actually building this rather than improvising a bring-up sequence — each stage exists to isolate a specific class of failure from the ones before and after it.

## Files

- `main.py` — the firmware entry point. Initializes the PMW3360 (SPI0) and ICM-42688-P (I2C0), then runs the fusion loop from `DESIGN.md` §6: integrate gyro yaw into heading, apply the lever-arm correction (`LEVER_ARM_MM = 18.0`, from the CAD), rotate into world coordinates, accumulate (x, y), and log every sample as a CSV row to `track_log.csv` on flash (flushed every `FLUSH_EVERY` samples — deliberate, given §4's power-reliability story makes a mid-run brownout a real risk, not a theoretical one). Stops after `LAPS_TO_RECORD` lap-marker crossings (IR sensor on GPIO26/ADC0) or `MAX_RUN_MS`, whichever comes first, resetting (x, y) to (0, 0) at each crossing. Read the module docstring before trusting a run — it lists the calibration steps not yet done (real SROM firmware, `LAP_THRESHOLD` against the actual marker, gyro-sign/optical-axis sanity checks).
- `pmw3360.py` — PMW3360 SPI driver (register map, motion-burst read, CPI-to-mm conversion). `SROM_FIRMWARE` is a zeroed placeholder, not the real firmware blob — see the module docstring for why, and what to replace it with.
- `icm42688.py` — ICM-42688-P I2C driver (WHO_AM_I check, low-noise mode config, raw/converted gyro+accel reads). Only gyro Z feeds the fusion loop today; accel is read but unused, kept for future crash-detection/roll-pitch work.
- `a6_binary.py` — **historical, not used by current firmware.** A desktop-only conversion script (adapted from `mrjohnk/ADNS-9800`) that embeds the *ADNS-9800's* SROM as a `frame` byte array and writes it to `adns_9800_srom_a6.bin` when run with `python a6_binary.py` on a regular computer. Left in place as a worked example of "how to turn a vendor SROM binary into a Python byte array" — that's the technique still needed for `pmw3360.py`'s placeholder, just with the PMW3360's own SROM file instead of the ADNS-9800's.
- `wifimanager.py` — an async `WiFiManager` class (`network` + `asyncio`, MicroPython-only) that connects to a list of known SSIDs and monitors/reconnects. Hardcoded `WIFI_NETWORKS` credentials near the bottom are placeholders. Standalone: not currently imported by `main.py`.
- `README.md` — the *original* design notes/scratchpad, from before this project settled on PMW3360/ICM-42688-P/Pico 2 W — largely superseded by `DESIGN.md` now. Its SROM/SD-card conversion walkthrough is ADNS-9800-specific and no longer the plan.
- `cad/fixture.scad` — parametric OpenSCAD model of the front sensor fixture (`DESIGN.md` §7). All donor-chassis dimensions are now from calipers (total fixture length is a measured 65mm, not the original ~112mm photo estimate — tight enough that the Pico 2 W is mounted rotated 90° to fit). Still not print-ready: component footprints (PMW3360/ICM-42688-P/IR module) are typical/placeholder pending the actual parts bought, and the rear splice joint is a placeholder pending the real spine cross-section. Render with `openscad --autocenter --viewall -o preview.png cad/fixture.scad`; its `echo()` output reports the computed fixture length, the lever-arm `r` for the fusion loop's correction (`DESIGN.md` §2), and flags any sensor standoff that comes out negative.
- `electronics/electronics.kicad_sch` — single-sheet KiCad schematic covering every electrical component (`DESIGN.md` §3 addendum): rail power input, reverse-polarity protection, buck-boost regulator, supercap (with an R1+D2 charge-inrush limiter — DESIGN.md §4), Pico 2 W, PMW3360, ICM-42688-P, IR reflectance sensor. Passes ERC clean. The GPIO pin assignments it settled (SPI0 on GPIO10-13, PMW3360 MOTION on GPIO14, I2C0 on GPIO4/5, ICM interrupt on GPIO6, IR sensor on GPIO26/ADC0) are exactly what `main.py` uses. Regulator/sensor modules are drawn as generic labeled connectors, not real part symbols — see the schematic's own text notes. `electronics/preview.png` is a rendered reference; regenerate with `kicad-cli sch export svg`.

## Architecture notes

- **PMW3360 protocol** (`pmw3360.py`): SPI register device, write with the MSB of the address set (`reg | 0x80`), read with it clear (`reg & 0x7F`). Bring-up is reset → discard stale motion registers → upload SROM firmware via burst mode → verify product ID (0x42) and SROM ID → set resolution (CPI). Steady-state reads use `Motion_Burst` (0x50), a single 12-byte burst covering motion status + delta X/Y + quality, rather than separate register reads.
- **ICM-42688-P protocol** (`icm42688.py`): I2C, `WHO_AM_I` (0x75) should read 0x47. `PWR_MGMT0` enables gyro+accel low-noise mode; needs ~50ms settling before readings are valid. Accel+gyro XYZ read as one 12-byte burst starting at `ACCEL_DATA_X1` (0x1F) — the two blocks are contiguous.
- **Fusion loop** (`main.py`, `DESIGN.md` §6): per tick, integrate gyro Z into heading, pull (dx, dy) off the PMW3360, apply the lever-arm correction, rotate into world frame, accumulate (x, y), log a CSV row, flush periodically. Lap crossings (IR sensor, debounced) reset (x, y) to (0, 0) and stop the run after `LAPS_TO_RECORD`.
- **Not done yet**: the real PMW3360 SROM firmware (placeholder in `pmw3360.py`), on-hardware validation of everything above, `LAP_THRESHOLD` calibration, and wiring `wifimanager.py` into `main.py` if live streaming (instead of a post-run file pull) is wanted later.
